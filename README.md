# GANGSTERS CLUB

A complete full-stack private-membership club platform. Cinematic public site,
application-and-approval membership flow, member dashboard with QR-verifiable
digital ID cards, and a full admin control center.

**There is no payment functionality anywhere in this project.** Membership is
granted exclusively through application + admin approval.

```
GANGSTERS CLUB/
├── frontend/      React + Vite + Tailwind (public site, member area, admin)
├── backend/       Express REST API
└── supabase/      schema.sql — tables, RLS, secure RPC functions, storage
```

## Stack

| Layer | Technology |
|---|---|
| Frontend | React, Vite, Tailwind CSS, React Router, Lucide |
| Backend | Node.js, Express (REST) |
| Database | Supabase PostgreSQL |
| Auth | Supabase Auth (email/password) |
| Storage | Supabase Storage (avatars, media) |
| QR | `qrcode` (open-source) |

Free-tier friendly across the board.

## 1. Database (Supabase)

1. Create a project at [supabase.com](https://supabase.com).
2. Open **SQL Editor** → New query.
3. Paste the entire contents of [`supabase/schema.sql`](./supabase/schema.sql) and run it.

This creates every table, index, trigger, Row Level Security policy, the secure
RPC functions (`approve_application`, `reject_application`, `suspend_member`,
`reactivate_member`, `verify_member`) and the storage buckets.

## 2. Backend

```bash
cd backend
cp .env.example .env      # fill in values from Supabase: Settings > API
npm install
npm run seed              # creates the initial administrator
npm run dev               # http://localhost:5000
```

Required env vars (see [`backend/.env.example`](./backend/.env.example)):

- `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` — the
  service-role key stays server-side and is **never** exposed to the browser.
- `PUBLIC_URL` — public site base URL. Used to build QR verification links: the
  backend passes it to `approve_application()` so every issued card encodes
  `<PUBLIC_URL>/verify/<MEMBER_ID>`.
- `CLIENT_URL` — frontend origin for CORS.
- `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` — used only by the seed script.
  The admin role is stored in the database (`profiles.role = 'admin'`); no
  admin credentials exist in source code.

## 3. Frontend

```bash
cd frontend
cp .env.example .env      # VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_API_URL
npm install
npm run dev               # http://localhost:5173
```

Build: `npm run build` → static output in `frontend/dist`.

Tests: `npm test` (Vitest + Testing Library, jsdom). The suite smoke-renders the
real app (`src/__tests__/routes.test.jsx`), covers the ErrorBoundary fallback,
the per-page titles and the Tailwind theme scales. `npm run test:watch` for
watch mode. `src/test/setup.js` stubs `fetch`, so the tests never touch the
network — pages must degrade gracefully on empty API payloads, which is exactly
what the smoke tests assert.

## The membership flow

```
Visitor → Apply → application stored (PENDING)
       → Admin reviews in dashboard
       → APPROVE: approve_application() RPC runs atomically
           · application → APPROVED
           · membership row created (unique GC-YYYY-NNNNNN)
           · profile role → member, status → active
           · member_verification row created (QR identity)
           · member notified
       → Member logs in → dashboard + digital ID card + Vault access
       → REJECT: status → REJECTED, optional reason stored, member notified
```

Member IDs are generated by a Postgres sequence (`generate_member_id()`), never
on the frontend. QR codes encode `<PUBLIC_URL>/verify/GC-2026-000001`; the
verification page performs a live registry lookup and returns only public fields
(name, member ID, status, join date) — never email, phone or date of birth.

## Security model

- Every protected API route verifies the Supabase JWT, loads the profile and
  checks the role **server-side** (`adminRequired` / `activeMemberRequired`).
- Row Level Security is enabled on every table as a second layer.
- Destructive or state-changing admin actions are RPCs guarded by
  `security definer` functions. `EXECUTE` on them is revoked from `PUBLIC`,
  `anon` and `authenticated` and granted only to `service_role`, so they cannot
  be invoked from the browser through PostgREST — the Express backend is the
  only caller.
- File uploads are MIME- and size-validated (5MB, JPG/PNG/WebP/AVIF).
- Rate limiting on auth and upload endpoints; zod validation on all input.
- Supabase `anon` key only in the frontend. The service-role key is backend-only.

## Roles & access

| Route | Who |
|---|---|
| `/`, `/about`, `/membership`, `/news`, `/events`, `/verify`, `/apply` | Public |
| `/login`, `/reset-password` | Public (redirects when signed in) |
| `/member/*` | Authenticated + approved, active membership |
| `/admin/*` | Authenticated administrator |

Suspended members are redirected to `/suspended` and lose all member-only API
access. Non-members attempting the Vault get `403`. Non-admins attempting
`/admin` are redirected to `/unauthorized`.

## Deployment

### Frontend → Vercel

1. Push the repository to GitHub.
2. Import the repo in Vercel.
3. Set the root directory to `frontend`.
4. Add environment variables: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`,
   `VITE_API_URL` (your deployed Render API URL).
5. Deploy. Framework preset: **Vite**.

### Backend → Render

1. New → **Web Service** from your GitHub repo.
2. Root directory: `backend`.
3. Build command: `npm install`
4. Start command: `npm start`
5. Add environment variables: `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`, `PUBLIC_URL`, `CLIENT_URL`, `PORT`.
6. Deploy, then point `VITE_API_URL` at the Render URL and redeploy the frontend.

### Supabase

The free tier covers database, auth and storage for launch. No paid services are
required.

## Flows to verify after deployment

1. Visitor applies → application appears in **Admin → Applications**.
2. Admin approves → membership created, unique Member ID issued, activity logged.
3. Member signs in → dashboard shows status, ID and Member ID.
4. Member ID card → QR → public `/verify/GC-2026-000001` shows correct status.
5. Admin publishes news → it appears on the public `/news` immediately.
6. Admin posts a member announcement → members see it + notification badge.
7. Admin suspends a member → member loses `/member/*` access.
8. Non-admin attempts `/admin` → access denied.
9. Non-member attempts the Vault → access denied.
10. Every breakpoint from 360px → 1440px+ renders without horizontal overflow.

## What is intentionally absent

Payments, subscriptions, checkout, AI features, crypto/blockchain, and any
third-party paid SaaS. Nothing in this repository processes money.
